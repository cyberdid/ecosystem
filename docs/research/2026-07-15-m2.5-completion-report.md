# M2.5 completion report

**Status:** implemented and verified for the embedded Linux/WSL read-only topology

**Date:** 2026-07-15

> Historical sub-milestone report. Its “Next gate” was completed later the same day; see the [M2 completion report](2026-07-15-m2-completion-report.md).

## Outcome

M2.5 closes the durable execution gap between the M2 policy contracts and the Linux repository reader. SQLite is the single transaction authority for run lifecycle, exact plan/decision bindings, absolute budgets, repository-read PREPARE/COMMIT, sanitized outcomes, and replay caches. The broker is filesystem-only; the typed orchestrator owns sequencing and calls the configured pure `PolicyEngine` before it spends authority.

This is a bounded embedded security profile, not a production-autonomy claim. It covers one process composition root, multiple SQLite connections/processes, a private local artifact CAS, and the Linux/WSL `openat2` backend.

## Implemented slices

### Authoritative event journal

- Schema v3 stores one immutable full `RunProjection` baseline and an immutable per-run event chain.
- Native runs start at `NEW` and persist `run.received`, `run.validated`, `plan.created`, policy, adapter, tool, artifact, and terminal events.
- Imported v2 histories are marked `historyComplete=false`; no missing historical event is invented.
- Sequence, previous digest, event digest, timestamp monotonicity, producer, configured issuer, subject, result, reducer semantics, cached state/head/sequence, terminal timestamp, and record/table inventories are verified on every reopen.
- Policy, tool result, operation, decision, and artifact bindings are reconciled in both directions.

### Single execution authority

- `RepositoryReadBroker` performs only descriptor-anchored filesystem reading and snapshot/content checks.
- `EmbeddedOrchestrator` re-evaluates the supplied tool decision through its configured `PolicyEngine`, then performs `PREPARE → broker read → artifact fsync → SUCCESS/FAILURE`.
- SQLite consumes decisions, spends tool attempts, reserves/commits/releases input bytes, owns leases, and records exact outcomes.
- Raw repository paths and content never enter the SQL journal; path references use a separate stable HMAC key.

### Crash and recovery profile

- Repository reads declare `recovery_mode=no_retry` because raw recovery payloads are deliberately absent from SQLite.
- An expired PREPARE cannot be reclaimed for repeated I/O. Resolution requires the exact observed fencing epoch, writes a deterministic sanitized failure, releases reserved bytes, and preserves the spent tool attempt.
- Process-exit tests use `fork` plus `os._exit` after PREPARE and prove fail-closed reopen/resolution.
- Concurrent writer/verifier and competing budget transactions prove coherent SQLite snapshots and conditional no-overspend.

### Durable artifacts and checkpoints

- The private content-addressed artifact store streams SHA-256/length, writes `0600` temporaries, fsyncs bytes, atomically installs without clobbering, fsyncs directories, and returns an HMAC availability proof without a filesystem path.
- SUCCESS requires the exact proof before SQL COMMIT. Reopen re-hashes every referenced successful artifact.
- Temporary crash debris is safely collected; object deletion is intentionally unavailable without an authoritative retained-reference set.
- Store-generated terminal checkpoints include the full reducer projection, history completeness/source, event head/sequence, budget cache, plan digest, and open-operation inventory. Generic checkpoint insertion is rejected.

### Operational persistence

- Authenticated v2→v3 migration verifies v2 metadata, audit HMAC chain, and immutable records before one atomic schema/meta transition; imported runs receive full projection baselines, not synthetic events.
- Online SQLite backup uses the SQLite backup API, immutable read-only semantic verification, exact-byte SHA-256, an authenticated canonical manifest, fsync, and no-overwrite publication.
- Restore authenticates and semantically verifies before no-overwrite publication.
- Dual-authenticated key rotation records a single-use nonce, retains historical verification keys, atomically updates the active meta key, and leaves path-reference digests stable through a separate key.
- External anchors bind store identity, schema, audit sequence/head, and the previous anchor. Startup can require an anchor. A real guarantee exists only when the caller supplies an independent append-only/WORM sink; `MemoryAnchorSink` is tests only.

## Verification matrix

| Property | Representative proof |
|---|---|
| Event replay and cache equality | native NEW→SUCCEEDED test; event/table/binding tamper reopen tests |
| No synthetic imported history | authenticated v2→v3 migration with `historyComplete=false` baseline contract |
| One durable budget authority | concurrent PREPARE limit and exact commit/release tests |
| Broker has no policy/budget authority | filesystem-only broker API and orchestrator integration tests |
| No raw path/content in SQLite | sentinel scans of DB/WAL/SHM and sanitized broker failure tests |
| No duplicate I/O after crash | process exit after PREPARE plus `no_retry` recovery test |
| Artifact exists before SUCCESS | CAS availability proof required by store COMMIT and reopen verification |
| Backup/restore integrity | WAL-capturing online backup, tamper/wrong-key/mutating-verifier/no-overwrite tests |
| Rotation continuity | old+new audit entries verified after reopen; stable path digest assertion |
| Audit rollback detection | external anchor prefix/exact-head/tail-rollback tests |

## Explicit proof boundary

- Opaque Python capabilities and pinned issuer labels are trusted in-process composition guards, not cryptographic identities for arbitrary remote processes.
- SQLite/HMAC detects modification but an independent sink is required to detect valid tail deletion outside a retained anchor.
- `synchronous=FULL` plus fsync is tested against process crashes, not laboratory power-loss or faulty-storage behavior.
- Artifacts are currently ephemeral CAS objects; full database-plus-blob disaster-recovery packaging and retention GC require an explicit retention/reference policy.
- Trusted snapshot generation, signed adapter observations, provider/model invocation, OS credential/network isolation, Windows/macOS brokers, and deployment parity are M2.6/M2 exit work.

## Historical handoff, later superseded

At this checkpoint, the proposed next gate named one DGX adapter and one cloud adapter. ADR-016 later removed the branded-hardware dependency after the DGX node became unavailable. The gate was fulfilled with one governed local Ollama deployment and one governed cloud Claude transport under the same evaluation mechanism. The cloud model name remains an observable provider alias, not an immutable-weight revision; dated capability observations require renewal after expiry.
