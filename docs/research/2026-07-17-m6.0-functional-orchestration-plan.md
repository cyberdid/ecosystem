# M6.0 research synthesis and implementation plan

**Date:** 2026-07-17  
**Status:** reviewed design baseline; not an implementation-completion claim  
**Scope:** universal AI ecosystem functionality independent of laptop, provider,
model, harness or optional GPU node

## Executive conclusion

The project has a real and unusually strong trust foundation, but the independent
2026-07-16 reviews correctly identified the product gap: policy, audit, recovery and
authority are much more mature than useful skills, general loops, model roles,
memory and agent teams. The next milestone must connect that foundation to daily
work without bypassing it.

The correct first use case is a fixed offline `source-review`, not a general agent
framework. It is broad enough to exercise source ingestion, model execution, roles,
handoffs, verification, budgets, recovery and terminal gates, yet narrow enough to
test exhaustively. It has no source-network, shell, tool or workspace-write
authority. After this vertical slice, M6 generalizes each proven primitive in a
separate gated slice.

### Internal independent reviews

The four Claude/Fable 5 reports added on 2026-07-16 converge on the same finding:

- M1–M5 are credible bounded infrastructure;
- practical daily value is still low because no live model-assisted useful loop is
  connected to the enforcement path;
- skills, roles, routing, memory and teams are essential product functionality;
- the system must stop measuring progress primarily by policy code and milestone
  labels;
- completion needs an independent reviewer/gate, not author self-attestation.

This M6 plan accepts the functional diagnosis while retaining the earlier security
boundaries. It does not implement the suggested shortcut of directly calling an
adapter from a loop, because code audit found that the current model adapter lacks a
durable governed composition path.

## Comparative analysis

### OpenResearcher

OpenResearcher is closest to a research-training/evaluation node. Its reusable ideas
are decomposed research tasks, structured trajectories, offline search/evaluation
patterns and grading datasets. Those are useful for future role fixtures and M6.7/M8
evaluation.

It is not the ecosystem runtime:

- training and evaluation architecture do not create local policy authority;
- trajectories are evidence/data, not trusted handoffs by default;
- research quality benchmarks do not prove source-integrity, prompt-injection,
  budget, crash or privacy guarantees;
- unrestricted research/search behavior cannot be placed on the trusted path;
- its model/data assumptions must remain optional behind adapters.

Decision: adopt bounded task/evaluation patterns after normalization; do not vendor
the runtime or treat its outputs as verified.

### OpenScience

OpenScience is the closest reference for an end-user research workbench. It shows
how skills, workflows, scientist roles, document/artifact generation and iterative
methodology can feel coherent to a user. It is strong inspiration for future
research profiles and M6.2/M6.3 packaging.

The audit also found reasons not to make it the core:

- safety and provenance defaults are weaker than this project's contracts;
- mutable skills/catalog state creates supply-chain and reproducibility risk;
- cloud and external-service coupling are implementation choices, not universal
  contracts;
- provenance and workflow claims need independent revalidation;
- code/config/plugin execution cannot be accepted from source material.

Decision: borrow workbench and methodology-packaging concepts; reimplement them as
locked, non-authorizing profiles and bounded loops.

### NVIDIA MOLT

MOLT explores agentic reinforcement learning, asynchronous generation/training and
token/trajectory-sensitive evaluation. It is strategically interesting once the
ecosystem has stable trajectories and a safe experiment boundary.

It is not orchestration infrastructure:

- it assumes a training/GPU stack and a much larger operational surface;
- learning loops introduce dataset poisoning, reward hacking, resource and model
  supply-chain risks;
- training output cannot automatically become a production deployment or trusted
  capability observation;
- the user no longer has a DGX, and no specific hardware may be a core dependency.

Decision: retain as an optional later training node behind M6 contracts and a future
experiment profile. Local CUDA/NIM can be one deployment, never the architecture.

### Multi-model team article

The supplied article correctly emphasizes role specialization, shared project
context, handoffs, independent checking and model diversity. These principles align
with the desired ecosystem.

The architecture must make them enforceable rather than prompt-only:

- a role is a versioned contract plus policy ceiling, not a persona string;
- a handoff is a typed artifact, not an unbounded transcript;
- a reviewer cannot mark its own artifact independently verified;
- using one model in five roles is valid orchestration but not multi-model
  independence;
- vendor or benchmark claims remain hypotheses until pinned evaluation evidence
  exists;
- source text cannot change system roles, tools or routes.

Decision: retain the conceptual team shape and translate it into records, budgets,
typed message channels and hard gates.

## Gap analysis against the current repository

| Needed capability | Current state | Required M6 correction |
|---|---|---|
| Skills | `skills/` is a placeholder | Canonical package format, lock, provenance, evaluation, projection, rollback |
| Harness sync | Instructions project to five clients; skills/hooks/agents do not | Capability matrix and deterministic honest degradation per harness |
| General loops | One fixed no-model wiki check | Versioned LoopDefinition and generic bounded executor |
| Model roles | Logical roles exist in deployments | First exact pin; later deterministic policy router and explanations |
| Model execution | Adapter exists, but no durable model operation in store | Policy authorization, PREPARE/start/complete/fail, CAS output, no-retry recovery |
| Context | One opaque adapter `input_text` | Typed system/task/untrusted-source channels and exact context artifacts |
| Memory | Wiki exists; no governed runtime memory | Namespaced provenance graph with trust/data/TTL/supersession/conflict |
| Teams | M5 controls human/team authority | Separate workload DAG, narrowed delegation, task claims and handoffs |
| Research tools | External research projects reviewed only | Later brokered allowlisted search/fetch with egress and provenance |

The model-execution gap is the critical dependency. A direct adapter call from a
team would bypass durable model request accounting, model-result journaling and
crash ambiguity. It must be closed before the visible team workflow is implemented.

## M6.0 decisions

### Decision 1 — functional M6, enterprise M7

Reassign M6 to Universal Functional Orchestration. Move the previous
enterprise/network/native-backend backlog to M7 without weakening or deleting it.
This is recorded as ADR-027.

### Decision 2 — additive orchestration namespace

Create `orchestration.ai.ecosystem/v1alpha1` and its own schema-bundle digest. Do
not add M6 records to `RUNTIME_SCHEMA_BY_KIND` or change the pinned M4/M5 runtime
schema digest. This is recorded as ADR-028.

### Decision 3 — one fixed vertical slice

The first workflow is package-owned and exact:

```text
planner → analyst → verifier → synthesizer → reviewer
```

It is manual, sequential, local-source-only, proposal/report-only and permits one
bounded synthesis/review revision. Normal maximum is five model requests; absolute
maximum is seven. It uses one explicit `local-loopback` deployment pin and a
zero-cost budget in M6.1, so no multi-model independence or provider-billing claim
is made. Trusted price catalogs and cloud-cost routing are deferred to M6.4.

### Decision 4 — model bridge before team runner

Add an exact policy-authorized durable model operation with budget reservation,
started fence, CAS result, atomic settlement, sanitized failure and conservative
recovery. Only then expose `eco team run source-review`.

### Decision 5 — generalization follows evidence

M6.2–M6.7 generalize skills, loops, routing, memory, teams and research tools only
after the fixed slice demonstrates the primitive and its adversarial tests. External
systems remain optional nodes/adapters.

## Detailed implementation sequence

### M6.0 — foundation

Deliver:

1. ADR-027 roadmap re-sequencing;
2. ADR-028 additive orchestration plane;
3. architecture and threat model;
4. exact record inventory and schema/version rules;
5. source-review trust boundaries and acceptance gates;
6. registered source provenance and comparative analysis;
7. baseline regression and old schema digest pin.

Exit: reviewable documentation with no functional claim, full 474-test baseline
green and no mutation of M1–M5 contracts.

### M6.1a — governed model execution

Deliver:

- exact `PolicyEngine.authorize_model` semantics;
- durable model PREPARE/start/complete/fail/ambiguous lifecycle;
- model request/output/token/cost budget accounting;
- typed instruction/task/source messages with tools disabled;
- private CAS output and content-free journal;
- pre-start resume and post-start no-retry recovery;
- deterministic scripted executor tests plus optional live local evidence.

Exit: no code path can perform a workflow model call outside the authorized durable
bridge.

### M6.1b — fixed source review

Deliver:

- bounded SourceBundle manifest/import;
- additive orchestration schemas and record validation;
- five-role state machine and typed handoffs;
- claim/evidence/verification/review graph;
- one revision edge and no-progress stop;
- exact hard gate and truthful terminal result;
- production CLI using only real configured deployments;
- deterministic injected executor only in tests;
- installed-wheel offline smoke and repository-identity proof.

Exit: a useful report is produced with zero source-network, tool and workspace-write
actions, exact budgets and replay-safe evidence.

### M6.2 — skills and harness sync

Deliver a canonical skill registry containing stable ID/version/source commit,
content digest, license, owner, capabilities, dependencies, tests, evidence,
revocation and compatibility. `eco skills plan/sync/check/uninstall` must never
execute discovered code, overwrite unmanaged files or silently degrade.

Start with three dogfood skills:

1. ecosystem contract changes;
2. loop authoring and hard stops;
3. source review and citation/evidence discipline.

Project deterministically to Codex, Claude, Gemini and a generic portable form.
Copilot/Cursor receive an honest supported subset. Lockfile, ownership marker,
atomic rollback and adversarial path/case/Unicode/link tests are required.

### M6.3 — generic bounded loop engine

Extract proven source-review state and recovery mechanics into an engine with closed
transitions, immutable objective/gate, attempts, deadline, tokens/cost/storage,
retry allowlist, no-progress detection, cancellation, kill switch and exactly one
terminal state. Port `wiki-health-check` as a compatibility profile; keep controlled
writes behind M3 approvals.

### M6.4 — logical roles and routing

Introduce canonical roles such as `eco-orchestrator`, `eco-worker`, `eco-grader`,
`eco-researcher` and `eco-coder`. Resolve each request deterministically from
role+data class+policy+observed capability+context+zone+retention+cost+deadline.
Emit a sanitized explain record. No candidate is a typed denial. Fallback requires a
fresh route decision and an explicitly retryable transport/capacity failure; policy,
privacy and authority denials never fallback.

### M6.5 — context, memory and handoffs

Add a private, namespaced artifact graph for facts, claims, decisions, constraints,
open questions, failed approaches and summaries. Preserve source digests, data
class, P-level, author, timestamp, TTL, supersedes/refutes links and conflicts.
Retrieval assembles bounded context; memory never grants tools, route, role or
policy. Compaction must remain reversible to exact sources.

### M6.6 — general agent teams

Generalize the exact role DAG into signed/locked manifests, bounded task claims,
narrowed child authority, aggregate budget reservations, typed handoffs, cancellation
and truthful partial failure. Add correct action-specific M5 team binding for
`model.invoke`; do not reuse the repository resource/subject equality shortcut.

### M6.7 — governed research tools

Add brokered search/fetch only after source-review is safe offline. Policies bind
allowed domains, redirects, size/media/time, credentials, query/data classification,
egress and retention. Retrieved bytes enter SourceBundle/CAS with provenance and
remain untrusted data. Browser cookies and arbitrary authenticated sessions are out
of scope until separately governed.

### M6.8 — conformance and release

Release `0.8.0` only after:

- complete M1–M6 regression;
- Python 3.11/3.12 contract gates;
- Linux CAS/crash/concurrency/isolation tests;
- focused macOS/Windows pure contract/sync tests with explicit non-claims;
- exact old/new schema digests;
- canonical validate/render/check/doctor;
- offline wheel contents and installed CLI smoke;
- leak-sentinel scans and repository byte/mtime identity;
- source-review dogfood run and independent review;
- a completion report that distinguishes deterministic evidence from optional live
  provider observations.

## Test and verification program

The detailed adversarial matrix is normative in the M6 threat model. The highest
priority families are:

1. plan/role/gate/namespace substitution;
2. malicious source ingestion and prompt injection;
3. typed-message and tool-disable enforcement;
4. stale/forged/mismatched routes and provider responses;
5. unsupported claims and reviewer self-review;
6. global/per-role/concurrent budget overspend;
7. kill/crash at every adapter/CAS/journal/handoff boundary;
8. terminal replay with zero calls;
9. cross-project/team/run leakage;
10. secret/source/path/endpoint leak scans;
11. old schema/store/CLI compatibility;
12. installed-wheel offline operation.

Every negative test must assert the typed reason, absence of forbidden effects and
absence of adversarial bytes from public/control-plane surfaces.

## Success metrics

M6 progress is measured by demonstrated useful operation, not line count:

- one reproducible source review produces a useful artifact;
- all model calls traverse the governed bridge;
- replay produces no duplicate call or cost;
- unsupported claims remain visible;
- a different eligible deployment requires configuration/evidence change, not
  workflow code change;
- one canonical skill projects consistently to supported harnesses;
- at least one loop resumes after pre-effect crash and stops after ambiguity;
- a new project can adopt, validate, sync and run without depending on this laptop;
- every broader claim is tied to explicit conformance evidence.

## Explicit non-claims

M6.0 implements no team workflow. M6.1 deterministic fixtures will not prove model
truth, prompt-injection immunity, provider equivalence, independent reviewers,
third-party code safety, enterprise authority, native cross-platform isolation or
production readiness. NIM/CUDA on the user's laptop is a valuable optional local
profile, not a requirement. Claude, Codex, Copilot, Gemini, Antigravity and future
clients remain replaceable harnesses/adapters with different supported subsets.
