# Організація екосистеми в масштабі компанії

**Багатопроєктна, багатохарнесна, багатомодельна архітектура: підхід**

**Дата:** 2026-07-16
**Автор:** Claude (Fable 5), на запит власниці
**Статус:** пропозиція (локальна нотатка, не закомічена)
**Вхідна умова:** екосистема інсталюється в компанію з багатьма проєктами; потрібні різні skills, tools, MCP, hooks, команди агентів/субагентів, методології (openresearch, openscience тощо); моделі різні — локальні LLM, Claude, Codex, Gemini, Copilot.

## 0. Головний принцип (щоб не загубити)

Уся конструкція тримається на одному правилі, яке вже є в конституції проєкту: **кожна річ пишеться один раз у канонічному, machine-readable вигляді — і детерміновано проєктується в усі місця споживання.** Скіл пишеться раз — з'являється в Claude Code, Codex і Gemini. Політика пишеться раз — звужується в кожному проєкті. Роль моделі оголошується раз — мапиться на різні деплойменти в різних середовищах. Якщо десь виникає бажання «просто скопіювати вручну» — це дірка в архітектурі.

Друге правило: **нижчий рівень може лише звужувати вищий, ніколи не розширювати** (authority precedence, вже реалізовано в `.ai/instructions.yaml`). Проєкт не може дозволити собі те, що заборонила компанія; задача не може розширити те, що заборонив проєкт.

Третє: **спроможність без верифікації не існує.** Скіл, MCP-сервер, методологія чи модель потрапляє в реєстр лише з доказом (еваль, тест, рев'ю) — і з власником, і з процедурою виключення.

## 1. Ментальна модель: три площини × чотири рівні

Все, що є в екосистемі, живе в одній із **трьох площин**:

| Площина | Що це | Приклади | Хто змінює |
|---|---|---|---|
| **Контент** (що вміємо) | скіли, методології, шаблони loop-ів, ролі агентів, знання/wiki | SKILL.md, research-loop, maker/checker | будь-хто через рев'ю |
| **Політика** (що можна) | capability vocabulary, data classes, allowlists інструментів/MCP, ліміти, approval-правила | «код класу D2 не йде в хмару», «запис — лише під підпис» | платформна команда + security, підписується |
| **Виконання** (чим і де) | деплойменти моделей, харнеси, рантайм-брокери, ключі | Ollama на GPU-сервері, Claude API, WSL-раннер | платформна команда |

Розділення критичне: контент ітерують швидко і вільно; політику міняють повільно і під підписом; виконання — взаємозамінне за контрактом. Проблеми починаються, коли ці площини змішують (політика в промптах, контент у конфігу деплойменту).

І на **чотирьох рівнях** (кожен — git-репозиторій або тека в ньому):

```text
Рівень 0: ecosystem-core (org hub)        ← одна на компанію
Рівень 1: profiles (домени/дисципліни)    ← research, engineering, data, legal…
Рівень 2: проєкт (.ai/ у кожному репо)    ← сотні
Рівень 3: сесія/задача (task-local)       ← тисячі, ефемерні
```

## 2. Топологія репозиторіїв

### 2.1 `ecosystem-core` — організаційний хаб (рівень 0)

Один репозиторій, власник — платформна команда (AI enablement). Містить:

```text
ecosystem-core/
├── .ai/                      # канон організації
│   ├── org.yaml              # ідентичність, глобальні інваріанти
│   ├── instructions-base.yaml# базові правила для ВСІХ проєктів
│   ├── capabilities.yaml     # єдиний словник спроможностей (D/A/Z/P семантика)
│   ├── deployments.yaml      # реєстр СХВАЛЕНИХ деплойментів моделей
│   └── policies/             # підписані deny-all бандли (M5-механіка)
├── registry/
│   ├── skills/               # канонічні скіли (кожен: SKILL.md + evidence/)
│   ├── loops/                # методології-петлі (research, science, TDD…)
│   ├── agents/               # ролі та команди агентів
│   ├── mcp/                  # схвалені MCP-сервери (пін версій/хешів + скоуп)
│   └── hooks/                # канонічні автоматизації (pre-commit, session-end…)
├── profiles/                 # рівень 1: бандли під дисципліни
│   ├── engineering.yaml
│   ├── research.yaml         # openresearch/openscience живуть тут
│   ├── data-ml.yaml
│   └── compliance.yaml
├── src/                      # eco CLI + runtime (те, що вже збудовано)
└── dist/                     # підписані офлайн-релізи (M4.5.3 вже вміє)
```

Хаб **не є сервісом** — це git-репо + версіоновані релізи. Централізований сервер з'являється лише за виміряної потреби (принцип embedded-first уже в ADR-002/008 — він правильний і для компанії: п'ять проєктів не потребують control plane).

### 2.2 Профіль (рівень 1) — «дисципліна в коробці»

Профіль — це YAML-маніфест, що збирає з реєстрів усе потрібне для типу роботи:

```yaml
# profiles/research.yaml
apiVersion: ai.ecosystem/v1alpha1
kind: Profile
metadata: { name: research, version: 1.4.0, owner: research-guild }
skills:      [deep-research@^2, source-review@^1, citation-verify@^1]
loops:       [openresearch-sweep@^1, openscience-replication@^0]
agents:      [researcher, adversarial-verifier, synthesizer]
mcp:         [arxiv-mcp@1.2.0, zotero-mcp@0.9.1]
hooks:       [session-end-state-write]
modelRoles:
  eco-orchestrator: { minCapability: reasoning-high }
  eco-worker:       { minCapability: long-context }
  eco-grader:       { separateContext: true }   # чекер ≠ мейкер
policyNarrowing:
  network: [arxiv.org, openalex.org, doi.org]   # лише звуження org-політики
```

Профілі версіонуються семвером. Проєкт каже «я research@^1.4» — і отримує все разом, відтворювано.

### 2.3 Проєкт (рівень 2) — `.ai/` у кожному репо

Те, що M1 вже робить, плюс успадкування:

```yaml
# .ai/project.yaml (у репо продукту)
extends:
  core: ecosystem-core@0.9.x        # версія org-канону
  profiles: [engineering@^2, research@^1]
identity: { name: fraud-detection, dataClass: D3-confidential }
modelRouting:
  eco-worker: local-only            # D3 → хмара заборонена політикою, тут лише підтвердження
harnesses: [claude-code, copilot]   # що реально використовує команда
localSkills: [fraud-domain-glossary]
protectedPaths: [migrations/**, secrets/**]
```

`eco render` компілює: org-base + профілі + проєктні звуження → **проєкції для кожного харнесу** + синк скілів + конфіг hook-ів. Drift-check у CI кожного репо (`eco render --check`) — уже готовий механізм.

### 2.4 Сесія/задача (рівень 3)

Ефемерний контракт: `/goal` (ціль + об'єктивний критерій done + hard stop), бюджет, task-local context. Ніколи не розширює права; після завершення — запис у STATE.md проєкту. Це рівень, де живуть субагентні команди на конкретну задачу.

## 3. Механіка композиції

1. **Злиття детерміноване і трирівневе:** org-base → профілі (в оголошеному порядку) → проєкт. Конфлікт двох профілів = помилка `eco validate`, не «останній переміг».
2. **Narrowing-only enforcement на етапі validate:** спроба проєкту розширити org-allowlist (додати MCP поза реєстром, підняти data class, відкрити мережу) — це помилка компіляції, а не порушення в рантаймі. Дешевше зловити при рендері.
3. **Версіонування і дистрибуція:** хаб публікує підписані релізи (wheel + registry snapshot — M4.5.3 механіка). Проєкти пінять версію. Оновлення = PR у проєкт із бампом версії, який показує `eco diff` — що зміниться в проєкціях. Жодних «тихих» оновлень політик.
4. **Локальні винятки** — лише через `localSkills`/`localAgents` з тим самим форматом і рев'ю; локальна політика — лише звуження. Все, що виявилось корисним у двох+ проєктах, — кандидат у реєстр (шлях знизу вгору).

## 4. Реєстри спроможностей і їхній життєвий цикл

Єдиний цикл для скілів, MCP, loop-ів, агентів:

```text
propose → review → evidence → publish → sync → measure → deprecate
```

- **propose:** PR у `ecosystem-core/registry/...` за шаблоном (frontmatter: name, description, owner, дата, скоуп);
- **review:** власник реєстру + представник домену; для MCP — обов'язково security (це supply chain!);
- **evidence:** «немає спроможності без верифікації» — для скіла це еваль-набір або принаймні відтворюваний приклад до/після; для MCP — пін версії+хешу, перелік tool-ів і їхніх action classes; для loop-а — прогін L0–L2 гейта (M4-механіка вже існує);
- **publish:** потрапляє в реліз хаба;
- **sync:** `eco render` розкладає по харнесах (див. §6);
- **measure:** використання і фейли збираються (спершу — простий лог у STATE.md проєктів, дашборд потім);
- **deprecate:** датований запис + видалення з проєкцій наступним релізом. Реєстр без процедури смерті стає звалищем.

**MCP окремо:** реєстр фіксує сервер@версія+хеш, транспорт, перелік інструментів з D/A класами, і **скоуп даних** («цей сервер бачить лише public»). MCP — транспорт, не довіра (принцип уже в README): жоден сервер не отримує прав через сам факт підключення.

**Hooks:** канонічні автоматизації описуються раз (`registry/hooks/session-end-state-write.yaml`: тригер, дія, гейт) і проєктуються в native-формати: Claude Code hooks у settings.json, git pre-commit, CI job. Один канон — три виконавці.

## 5. Моделі: ролі, деплойменти, маршрутизація за класом даних

**Ключова розв'язка: код спілкується з РОЛЛЮ, політика мапить роль на ДЕПЛОЙМЕНТ.**

- Ролі (org-словник): `eco-orchestrator` (планування, найрозумніша), `eco-worker` (масова робота, дешева/локальна), `eco-grader` (верифікація, окремий контекст від мейкера), `eco-embedder`, за потреби доменні (`eco-coder`, `eco-researcher`).
- Реєстр деплойментів (рівень 0): кожен запис = точна ідентичність + спостережені capabilities + дозволені data classes + вартість:

```yaml
deployments:
  - id: local-ollama-qwen72b
    endpoint: http://gpu-node-1:11434   # transport: openai-compatible
    dataClasses: [D0, D1, D2, D3]       # локальний → можна конфіденційне
    observedCapabilities: obs-2026-07-…  # ADR-016: спостереження, не віра
  - id: cloud-claude-sonnet
    dataClasses: [D0, D1]               # хмара → лише public/internal
  - id: cloud-gemini-flash
    dataClasses: [D0]
routing:
  - { role: eco-worker, dataClass: D3, use: local-ollama-qwen72b }
  - { role: eco-orchestrator, dataClass: D1, use: cloud-claude-sonnet }
```

- **Маршрут = функція(роль, data class проєкту, середовище).** Проєкт із D3 автоматично отримує worker-а локально — не тому, що хтось пам'ятає правило, а тому, що інший маршрут не скомпілюється/не пройде policy.
- Транспорт: OpenAI-сумісний endpoint як спільний знаменник (Ollama, vLLM, LiteLLM, проксі) + прямі адаптери там, де семантика важлива (уже є: ADR-004 «API-сумісність ≠ семантична сумісність», спостереження capabilities по кожному деплойменту).
- Шлюз (LiteLLM тощо) — **опційна деталь виконання**: він зручний для spend caps і fallback-ланцюгів, але контракти й ролі живуть у `.ai/`, тому заміна шлюзу нічого не ламає.
- Харнесні моделі (Codex у своєму CLI, Copilot у своєму) напряму не маршрутизуються — ними керує проєкція інструкцій (яка каже агенту, коли делегувати роботу через `eco`-ролі, а що робити власною моделлю).

## 6. Харнеси: матриця проєкцій

Один канон → native-формати кожного харнесу. Це серце багатохарнесності:

| Артефакт канону | Claude Code | Codex | Copilot | Gemini CLI | Cursor |
|---|---|---|---|---|---|
| Інструкції проєкту | CLAUDE.md | AGENTS.md | .github/copilot-instructions.md | GEMINI.md | .cursor/rules/*.mdc |
| Скіли | ~/.claude/skills/ або .claude/skills/ | ~/.codex/skills/ | інлайн-секції в instructions | ~/.gemini/skills/ | правила/доки |
| Ролі агентів/субагентів | .claude/agents/*.md | секції AGENTS.md | — (обмежено) | — | — |
| Hooks | settings.json hooks | — → git-hook | — → CI job | — → git-hook | — |
| MCP | .mcp.json | mcp-конфіг Codex | — | gemini mcp config | mcp.json |

Правила:

1. **Проєктується лише те, що харнес уміє нести.** Якщо харнес не підтримує субагентів — роль не «емулюється мовчки», а деградує явно (NO-SILENT-DOWNGRADE вже must-правило): у проєкції з'являється секція «цей харнес не виконує ролі X — делегуй через eco».
2. Кожна проєкція несе ownership-маркер і дайджест (M1-механіка) — ручні правки ловляться drift-check-ом.
3. Найповніший харнес (сьогодні Claude Code: скіли+хуки+субагенти+MCP) — референс; решта отримують чесні підмножини. Це і є практична відповідь на «різні моделі»: команда проєкту обирає харнес, екосистема гарантує, що знання і правила однакові всюди.

## 7. Методології (openresearch, openscience тощо) як loop-пакети

Методологія — це не стаття у wiki, а **виконуваний пакет** у `registry/loops/`:

```text
registry/loops/openresearch-sweep/
├── LOOP.md          # контракт: тригер, скоуп, гейт, hard stop, кольори
├── SKILL.md         # як виконувати (для агента)
├── agents.yaml      # команда: researcher ×N → adversarial-verifier → synthesizer
├── gate/            # об'єктивна перевірка результату (цитати перевірені? джерела живі?)
└── evidence/        # прогони L0–L2 промоушну
```

- Кожен loop успадковує **4 артефакти + hard stop** (конституція) і **L0–L5 зрілість із промоушном за 5 відтворюваних прогонів** (M4-механіка вже реалізована);
- 🟢/🟡/🔴 межі: research-loop зазвичай 🟢 (читає/пропонує), openscience-replication 🟡 (драфтить артефакти під людський шип), будь-що з грошима/продом/аутбаундом 🔴 — ніколи саме;
- Зовнішні підходи (OpenResearcher, labs-molt, чужі скіл-пакети) проходять той самий шлях, що вже відпрацьований у репо: **downloaded → statically reviewed → wiki-сторінка з межами → gated adoption** — і лише потім стають loop-пакетом. Патерн уже є (wiki/openresearcher.md, labs-molt.md) — його треба лише формалізувати як процедуру реєстру.

## 8. Enforcement: три ступені, не один

Помилка — вмикати «поліцію» скрізь одразу. Правильно — три ступені за ризиком:

| Ступінь | Що захищає | Механізм | Коли достатньо |
|---|---|---|---|
| **1. Конвенції** | якість, консистентність | проєкції + drift-check + рев'ю | більшість проєктів, D0–D1, читання |
| **2. Гейти** | «done = доказ» | CI: тести, eco validate, loop-гейти, зовнішнє рев'ю «Complete» | усе, що мержиться; 🟡 loop-и |
| **3. Рантайм** | дії агентів як такі | M2/M3 брокери: policy+approval+CAS+журнал на Linux-раннерах | D2+, записи агентів, 🔴 операції, регульовані дані |
| | | M5: підписані політики, кворум різних людей | багатокомандні права, прод |

Ступінь 3 розгортається **не на лептопах розробників**, а на виділених Linux-раннерах (CI runners, WSL, сервер команди) — там, де агенти виконують автономні петлі. Лептоп із Claude Code живе на ступенях 1–2; автономний loop, що вночі правіть wiki, — на ступені 3. Це знімає і «macOS-проблему»: макбук — кабіна, раннер — машинне відділення.

## 9. Governance: люди і ключі

- **Платформна команда (2–3 людини + агенти):** володіє `ecosystem-core`, підписує політики (Ed25519, M5), тримає реєстр деплойментів, проводить ключові церемонії, ганяє релізи;
- **Власники доменів/гільдії:** володіють профілями і реєстровими рев'ю свого домену;
- **Проєктні ліди:** обирають профілі, звужують політику, підписують M3-записи у своїх межах;
- **Security:** рев'ю MCP/зовнішніх нод, модель загроз, аудит-якорі;
- **Розробники:** користуються; пропонують у реєстр знизу вгору.
- Кворум різних людей (M5.6) — для org-політик і 🔴 операцій; сепарація maker/checker — за замовчуванням у всіх loop-ах.
- Ключі: org root (кворум, офлайн) → підписує team/profile ключі → підписують політики й approval-адаптери. Церемонії — заскриптовані і задокументовані (сьогодні це головна дірка — ADR-019 чесний, але церемонії немає).

## 10. Мапа на наявну кодову базу: що є, що добудувати

| Потрібно для компанії | Стан у кодовій базі | Робота |
|---|---|---|
| Канон + проєкції на репо | ✅ M1 (`eco render`, drift, adopt, uninstall) | — |
| Успадкування org→profile→project (`extends`) | ❌ `.ai/` зараз однорівневий | **П1: найважливіша добудова** |
| Реєстр скілів + синк у харнеси | ❌ (skills/ порожній) | **П1** |
| Проєкція субагентів/hooks у native-формати | ❌ | П2 |
| Ролі моделей + маршрутизація за data class | 🟡 словник capabilities/deployments є; ролей і routing нема | **П1** |
| Реєстр MCP із пінами й скоупами | 🟡 mcp/registry.json — заготовка | П2 |
| Loop-пакети з промоушном | ✅ M4-механіка (один loop) | П2: другий-третій loop |
| Enforcement читання/запису | ✅ M2/M3 (Linux) | П3: розгорнути на раннери + церемонія ключів |
| Підписані політики, ідентичності, кворум | ✅ M5-примітиви | П3: перша реальна активація |
| Дистрибуція версій у проєкти | ✅ M4.5 (adopt + wheel-дистрибутив) | — |
| Дашборд використання/дрифту по органзації | ❌ | П4 (спершу — просто CI-статуси) |

Висновок мапи: **найдорожче вже збудовано** (enforcement, дистрибуція, governance-примітиви). Бракує саме «клею для масштабу»: extends, реєстр скілів із синком, ролі моделей. Це тижні, не місяці.

## 11. Rollout у компанію (фази з критеріями виходу)

- **Фаза A — пілот (2–4 тижні):** hub-репо + 2–3 несхожі проєкти через `eco adopt`; лише ступені 1–2; 5–10 скілів у реєстрі; один research-loop. *Вихід:* команди пілоту користуються щодня; drift-check зелений у CI всіх пілотів.
- **Фаза B — профілі та реєстри (1–2 міс.):** видобути профілі з пілотів; життєвий цикл реєстру працює (перший deprecate!); ролі моделей + маршрутизація; 10–20 проєктів. *Вихід:* новий проєкт онбордиться за <1 години без участі платформної команди.
- **Фаза C — enforcement там, де треба (1–2 міс.):** Linux-раннери з рантаймом; церемонії ключів; перший 🟡→L3 loop із M3-записами під підпис; M5-політики для D3-проєктів. *Вихід:* перший автономний loop у проді з повним аудит-трейлом.
- **Фаза D — вимірювання:** метрики цінності loop-ів (скільки годин зекономлено, скільки правок прийнято), дашборд, і лише тут — розмова про центральні сервіси, якщо біль виміряний.

## 12. Анти-патерни (чого не робити)

1. **Не робити «AI-платформу» сервісом із першого дня.** Git + релізи + CLI масштабуються до десятків проєктів; сервер — після виміряного болю.
2. **Не пускати політику в промпти.** Промпт — гайдлайн; право — лише через validate/policy/runtime.
3. **Не дозволяти вендорські файли писати руками.** Побачив ручний CLAUDE.md — це дрифт, а не «швидка правка».
4. **Не приймати в реєстр без evidence і без власника.** Реєстр без цвинтаря (deprecate) стає звалищем за квартал.
5. **Не вимірювати прогрес звітами агентів.** «Complete» від автора коду не існує — лише зовнішній гейт (цей проєкт довів це на власному досвіді 2026-07-16).
6. **Не будувати наступний поверх, поки попередній не використовується.** Правило одного незакритого «замка»: у системі не може бути двох збудованих-але-не-використаних шарів одночасно.
