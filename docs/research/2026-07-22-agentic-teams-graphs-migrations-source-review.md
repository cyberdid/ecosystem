## Research question

Що з цих шести статей — надійний інженерний сигнал для vendor-нейтральної AI-екосистеми, що вже реалізовано в проєкті, що варто перейняти як примітив (skill/loop/контракт/методологія), а що — маркетинг, framework-lock-in чи патерн, який проєкт свідомо відкидає?

## Executive verdict

Продовження висновку 2026-07-20 підтверджується сильніше: **ринок сходиться на тезі, яку проєкт уже реалізує** — окремий рецензент замість автора, обмежені петлі з гейтами, механічна верифікація, tiering моделей, скіли як переносна одиниця, персистентна пам'ять, людина як фінальний дозвіл на гроші/відправку. Усі шість статей описують ту саму архітектуру різними словами.

Але ключова відмінність — **у способі досягнення**, і саме вона відповідає на попереднє питання власниці «як переконатись, що LLM виконає концепції»:

- **Статті досягають дисципліни двома крихкими способами:** (1) промпт-примусом («The framework literally shouts MUST in all caps») і (2) прийняттям стороннього фреймворку/продукту (Superpowers, Raft, Hermes, Google ADK, Claude-специфічні dynamic workflows). Перше — це категорія «чисто промптова» з мого попереднього аналізу enforcement: модель *може* відхилитися. Друге — прив'язка до вендора, що прямо суперечить меті проєкту.
- **Проєкт досягає тієї ж дисципліни enforced-контрактами** (broker/policy/gate/CAS), де порушення структурно неможливе або ловиться на виході незалежно від моделі.

Тобто ці джерела — не інструкція до наслідування, а **ринковий доказ, що проєкт будує правильну річ правильнішим способом**. Із них випливають рівно **три конкретні кандидати на роботу** (нижче), решта — вже реалізовано або свідомо відкинуто.

## Мапінг патернів на примітиви проєкту

### A. Уже реалізовано (джерело → наявний примітив)

| Патерн у статтях | Де в проєкті вже enforced |
|---|---|
| «No agent grades its own work» (teams, migrations, Superpowers) | Конституція + окремоконтекстний grader, M6 teams maker/checker |
| Механічна верифікація: compiler/test/diff як суддя (migrations) | **VERIFY-DONE**, детерміновані гейти M4/M6 (byte-exact цитати, coverage) |
| Loop = trigger + body + escalation (Hermes) | **BOUNDED-LOOPS** = trigger+body+gate+hard stop; M6.3 loop engine |
| Скіл як переносна одиниця + sync у харнеси (build-team, Karpathy ADK) | **M6.2** `eco skills` — 3 канонічні скіли → 5 харнесів + lockfile |
| Персистентна пам'ять між сесіями (Hermes, claude-mem) | **M6.5** memory graph; STATE.md-конвенція (ADR-018) |
| Людина — фінальний дозвіл на гроші/відправку (team, small-business) | **M3** approval (single-use, parameter-bound); 🔴 red-loops «ніколи сам» |
| Ізоляція / worktree / sandbox (Superpowers, Codex) | **M2** isolation (Landlock), **M3** CAS + compare-and-swap rollback |
| Tier моделей: дешева на масу, дорога на суд (migrations, graph) | Частково: словник `logicalRoles` + `allowedDataClasses` є; routing gap (нижче) |

### B. Вартісні нові сигнали — кандидати на роботу

1. **Graph-orchestration патерн** (стаття Codez). Fan-out → reduce → synthesize; diamond; verifier-на-edge; loop-until-dry з дедупом проти *всього побаченого*; pipeline vs barrier. Проєкт має **лінійний** bounded-loop engine (M6.3), не граф. Це реальний методологічний gap. **Застереження:** сама стаття описує Claude-специфічну фічу (Claude Code dynamic workflows) — переймати треба *патерн у vendor-нейтральний eco_loops*, не інструмент. Мапиться на: **методологічний патерн + розширення eco_loops**, не на прийняття продукту.
2. **«Validate the judge against broken code»** (migrations + Karpathy ADK). Обидві незалежно кажуть: суддя, який не ловить навмисно зламане, — не суддя; ганяй гейт проти зумисно поламаного коду. Це **прямо підсилює adversarial-suite**, який я пропонував для enforcement-питання: доказ, що правило fail-closed, вимагає atаки, а не лише позитивного тесту. Мапиться на: **методологія + новий тест-контракт** (детермінований, без LLM).
3. **Model-role separation / routing за data class** (усі, явно migrations+graph). 2026-07-20 review вже назвав це «the one gap»; ця хвиля підтверджує. Словник ролей є, детермінований routing за класом даних — незавершений. Мапиться на: **контракт `.ai/deployments.yaml` + eco_routing**.

### C. Свідомо відкинути (патерн → правило, що його відкидає)

| Патерн у статтях | Чому відкидаємо |
|---|---|
| Framework/продукт як залежність (Superpowers, Raft, Hermes, ADK) | **SCOPE-CONTROL** + vendor-нейтральність: переймаємо патерни в контракти, не рантайми |
| «MUST» у caps як механізм примусу | **POLICY-OUTSIDE-PROMPTS**: промпт — гайд, не authorization; enforcement у broker |
| Agent «souls» / self-written skills, авто-довірені | **VERIFIED-STATE**: пам'ять ≠ дозвіл; скіл потрапляє в реєстр лише з evidence + власником |
| Persistent daemon, що «runs shell commands on your behalf» (Hermes) | Isolation-first, **NO-DIRECT-EGRESS**: автономна дія лише за policy+approval на ізольованому раннері |
| «Hire 42 skills» — install стороннього каталогу | Кожен зовнішній скіл/MCP = untrusted supply-chain; шлях downloaded→statically reviewed→gated (як upstream-клони в MAP.md), не масовий install |
| Affiliate/спонсор/repost-CTA/Substack-промо | Маркетинговий шум; ігнорується |

## Зв'язок із питанням власниці про enforcement

Ці статті — найкраща наочна ілюстрація мого попереднього поділу концепцій на категорії:

- Домінантний ринковий підхід тримає дисципліну на **категорії 3** (промпт-примус «MUST») і на довірі до стороннього фреймворку. Обидва крихкі: модель може відхилитися, фреймворк — застаріти чи змінити ліцензію.
- Проєкт тримає ту саму дисципліну на **категоріях 1–2** (рантайм-enforcement + гейт на виході), що model-agnostic.

Найцінніший практичний висновок для «як переконатись, що концепції виконуються»: обидві Anthropic-міграції і Karpathy/ADK незалежно наполягають на **валідації судді проти зламаного коду**. Це і є конкретний метод — не «повір, що гейт працює», а «доведи, що він ловить поламане». Це посилює пропозицію adversarial-suite і дає їй перевірений ринком патерн.
