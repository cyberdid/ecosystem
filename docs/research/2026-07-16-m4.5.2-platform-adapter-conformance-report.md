# M4.5.2 platform and adapter conformance completion report

**Date:** 2026-07-16

**Scope:** contracts, passive doctor, portability fixtures, adversarial tests, documentation, and CI gate

## Executive result

M4.5.2 is implemented as a non-authorizing platform/adapter description layer. The ecosystem now has closed `PlatformProfile` and `AdapterCapabilityProfile` schemas, a deterministic `eco platform doctor --json`, and a six-profile fixture matrix. The command performs no installation, executable invocation, network access, repository mutation, adapter construction, credential resolution, or runtime-authority creation.

The key design result is negative but essential: discovery never becomes proof. Every runtime-security capability remains `not-tested`; `profile.proven` is null; `effectiveCapabilities` is empty. Authenticated backend-specific runtime `AdapterConformanceProfile` evidence remains the separate proof mechanism.

## Research and review method

The implementation used three specialized review tracks:

1. a contract track for state separation, schema closure, deterministic digests, and adapter/runtime evidence boundaries;
2. an adversarial test track for platform fixtures, spoofing, privacy, zero mutation, and cross-OS execution;
3. a security track for authority escalation, process/network/write side effects, evidence replay, path disclosure, nested contexts, and explicit non-claims.

The security review rejected an early idea to accept a local `PlatformConformanceEvidence` dictionary. Such an input would allow the same process that detects a platform to manufacture its own proof. The final API has no evidence parameter and cannot populate proven or effective state.

## Threat model

### Assets

- runtime authority and effective capability state;
- repository contents and metadata;
- credentials, endpoints, model identities, environment values, and host identifiers;
- trust in existing signed conformance evidence;
- deterministic cross-platform behavior.

### Adversaries and failures

- a caller supplies a false declared profile;
- mutable WSL/container/CI variables spoof a stronger platform;
- a crafted fixture contains unknown fields, duplicate ids, or a nested fake proof;
- an executable on the search path writes a sentinel if invoked;
- a probe exception contains a root path, token, endpoint, or username;
- a nested environment matches more than one profile;
- a schema-valid declaration is mistaken for authorization;
- Linux evidence is replayed for WSL, Windows, macOS, a container, or another deployment.

### Security decisions

- platform and adapter documents are content-minimized descriptors, never authority tokens;
- the doctor never reads evidence, signs evidence, or invokes a conformance workload;
- mutable environment hints cannot establish trusted identity;
- nested strong contexts fail as ambiguous in this version;
- executable discovery emits a boolean only and never invokes or reads the target;
- client `surface-present` means only a regular file exists at a fixed projection location;
- unknown input and unknown exceptions return fixed sanitized codes;
- proof remains the responsibility of the existing external trust and runtime-policy boundary.

## State and authority analysis

The capability chain is intentionally conjunctive:

```text
canonical capability
∩ operator declaration
∩ platform/backend support
∩ adapter declaration
∩ independently verified exact-bound evidence
= effective capability considered by policy
```

M4.5.2 supplies only the descriptive inputs to this chain. It does not implement the final policy intersection. The passive report contains no authenticated evidence and therefore cannot satisfy it.

`AdapterCapabilityProfile` is intentionally weaker than runtime `AdapterConformanceProfile`:

- the former can say what an adapter declares or what inventory observed;
- the latter records a governed suite result, exact deployment identity, validity interval, probes, deviations, and effective capabilities inside an authenticated envelope;
- the former structurally forbids proven state and fixes effective state false;
- the latter must still be re-verified by the runtime immediately before authority is used.

## Adversarial findings and resolutions

### Self-issued proof

**Finding:** accepting an unsigned local evidence object would allow detection to elevate itself.

**Resolution:** removed the evidence input entirely. Unknown nested evidence fields fail closed.

### Environment spoofing

**Finding:** `WSL_*`, `CI`, container, and CUDA variables are mutable.

**Resolution:** the public report does not enumerate raw environment state. A normalized hint without a corroborating categorical marker is blocked and never populates proven state.

### Nested contexts

**Finding:** WSL, container, and hosted-CI contexts can overlap, and choosing one loses important semantics.

**Resolution:** more than one strong context is `ambiguous` and blocked in v1alpha1. A future compositional profile requires its own schema and backend suites.

### Discovery side effects

**Finding:** a conventional doctor often runs `git`, `docker`, `nvidia-smi`, a shell, or an adapter endpoint.

**Resolution:** this doctor invokes none of them. Tests replace process, shell, socket, HTTP, and filesystem mutation primitives with traps. The repository before/after manifest remains byte- and mtime-identical.

### Privacy

**Finding:** paths, environment values, package/device inventories, and exception text can fingerprint a host or disclose secrets.

**Resolution:** output is restricted to fixed identifiers, enums, counts, booleans, and semantic digests over normalized categorical input. Paths returned by executable discovery are discarded. Exceptions become fixed codes.

### Contract confusion

**Finding:** the new adapter profile could be mistaken for the existing signed conformance record.

**Resolution:** the schema fixes its authority to declaration/inventory only, forbids proven/effective capability state, and documents the existing runtime record as the sole proof form.

## Residual risks and non-claims

The doctor is not a conformance runner, authorization oracle, package installer, endpoint health check, GPU validator, or sandbox test. It does not establish executable provenance, filesystem race safety, shell behavior, process containment, network denial, credential access, adapter functionality, model identity, client obedience, or loop eligibility.

The report digest detects change in normalized report semantics; it is neither a signature nor a secret. Local paths or host identifiers are deliberately excluded instead of being hashed, because low-entropy hashes remain fingerprintable.

The passive observation may become stale immediately after the command exits. Any consumer that later creates authority must independently verify fresh exact-bound signed evidence and re-check its own TOCTOU boundary.

## M4.5.3 handoff

Portable packaging is now the next bounded milestone. Its installer must consume these contracts without widening them, preserve M4.5.1 preview/apply/ownership behavior, and keep platform detection separate from installation. Native Windows/macOS runtime backends and a controlled external conformance runner remain separate work; packaging must not label them supported merely because the CLI and passive profiles run there.
